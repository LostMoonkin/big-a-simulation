## 顺序一：交付能核对账本的单批回放

在 `packages/sim-core` 建立不依赖 UI 的 TypeScript 包，在 `tools/sim-runner` 提供薄 CLI。复用 P0 锁定的 Node、包管理与测试工具版本，不另选一套精度库。

先用显式初始持仓和现金建立场景；包括固定创始持有人、普通账户和服务账户，使股票与现金审计从第一条成交开始成立。场景输入是有资金支撑的申报意图，不是预写股价、K 线或清算结果。

按规则依次实现资源校验、候选价枚举、最优价选取、双侧数量分配、统一价成交、汇总费用及原子记账。将 A01–A05 做成可以由 CLI 展示前后账本的样例；同价拆单和非限价清算点必须在实际程序中复现。

独立穷举器只在有界 tick 范围计算参考答案，不复用生产候选价选择函数；否则两边可能一起漏掉区间内部的平衡价。随机用例保存生成种子与失败输入，不只打印“断言失败”。

明确产物：初始 schema、可执行单批 CLI、五个具名场景、独立参考结果、按批守恒摘要。对应 P1-T1、P1-AC1/AC5。

## 顺序二：交付可暂停的完整订单过程

外部命令至少覆盖提交即时单、提交日单、创建分批计划、撤销、推进和读取公开状态。统一返回命令结果和回执；不得让 CLI 直接修改余额或订单剩余量。

实现订单/计划的活跃、部分完成、完成、撤销、到期状态；费用预留跟随剩余数量和最大剩余成交批数重算。计划是总量语义，NPC 目标缺口是目标持仓语义，提供不同的调用入口，不能共用一个含糊的“剩余量”字段。

将跨股票预算缩放、缩量后费用复核和稳定减量作为账户级能力实现。即便自主 NPC 尚未接入，也用固定意图验证 A08/A19；玩家超额订单明确拒绝，不悄悄替玩家缩单。

用一个共享钱包同时给两市场下单，包含部分成交后撤销、同一计划多批成交、当日到期及反向单拒绝。检查现金冻结是总现金的子集，售股冻结不超过当前可售股，逐批向上取整费用不会透支。

明确产物：三类订单的回放输入和回执、订单/计划状态快照、A07–A10/A19 结果。对应 P1-T2、P1-AC2/AC5。

## 顺序三：交付双市场时钟与公开窗口

以 `(worldDay, batch)` 驱动解锁、到期、公开、决策、清算和记账。每天 16 批、每四批一个小时；时间不依赖机器日期或真实等待。批间卖款可用和股份可售日期进入真实总账，而不只在表单按钮上禁用。

为 A12 使用小型场景参与者：它只能接收公共快照、自身账户和固定参数，公告前后按同一规则修订意图。工程诊断可读取全部快照，但该入口不能复用于参与者或 UI。

价格保护作为市场状态随快照保存，真实原始限价仍受资源约束。按 P0 冻结程序计算指示交叉、公告、保护变化及重新报价，不将无价格带试算当作交易；不存在交叉需求与被价格带阻断必须在日志里可区分。

分别演示旧股/新股、乙市场下一批退出、甲市场跨日解锁、卖款跨市场复用以及保护受阻后恢复。保持股票循环顺序的不同版本作对照，防止先处理某股就能提前花钱。

明确产物：A06/A11/A12/P0 更新后的 A13/A14 场景及可读过程日志。对应 P1-T3、P1-AC3/AC4/AC5。

## 顺序四：交付可移交的恢复与验收工具

建议外部边界为创建场景/世界、提交命令、推进到决策点、读取公共快照、导出完整快照、恢复快照；精确签名在实现中保持小而稳定。UI 与 CLI 共用这些入口，不能各自实现一份撮合或费用计算。

完整快照至少包含：格式/规则/数值协议版本、世界时点及已完成阶段、账户与股份解锁批次、有效订单/计划/冻结、市场保护和最近成交、公共信息版本与历史、独立随机状态、待处理命令及去重标记。P2/P3 新增的经营和行为状态从同一完整世界快照扩展。

只允许在稳定决策边界导出，其中包括公开准备已完成、NPC 尚未下单与清算的窗口，不要求为保存先完成该批交易。快照记录当前阶段，恢复后停在原窗口，不重复公告/解锁，也不先替玩家推进；交易清算产生的资源变更与记账原子提交。`commandId` 用于识别已经接收的命令，重试返回原结果而不重复下单；改变参数后复用 ID 明确拒绝。

序列化采用 P0 冻结的整数/大数编码和字段顺序。输入先验证格式、版本、资源关系及内容校验，失败不得改写当前世界。版本不兼容时明确拒绝；本阶段无需实现迁移。

随机流分别验证：重复读取/预览不消耗随机数；增加玩家订单不改后续外生抽样；不同批量推进方式不改变固定指令下的结果。市场反应因交易变化而改变是正常现象，不能为保持图表一致而共享预生成价格。

明确产物：可恢复 fixture、逐批状态摘要、P0 指定运行端回放结果、CLI 使用说明和阶段报告。对应 P1-T4、P1-AC6/AC7，并回归 P1 全部 AC。

## 接口与下一阶段衔接

| 边界 | 输入/输出合同 | P2 使用方式 |
|---|---|---|
| Command | 唯一 ID、目标世界边界、订单/撤销/推进意图 → 接受或拒绝回执 | Worker 收消息后原样调用，主线程不推算账本 |
| PublicSnapshot | 版本、公开行情/资料、本人账户和本人订单 | 表格、图表、交易表单只读该投影 |
| TransitionResult | 成交、费用、订单状态、暂停原因和新公开版本 | UI 按版本更新，不提前渲染未来 K 线 |
| FullSnapshot | 所有重放必要私有状态、版本与校验 | CLI 和本地文件导入导出；不作为 NPC 输入 |
| VerificationTrace | 稳定实体 ID、时点、守恒摘要、拒绝原因 | 批量经济测试定位错误；默认不公开其他账户内幕 |

## 核验命令与证据

以下脚本已落地；Windows PowerShell 用 `npm.cmd` 转发 `--`。实际执行结果与源码身份见实施报告，命令存在不授予阶段通过：

```text
npm run verify:p1 -- --out artifacts/verification/p1/<run-id>
npm run sim:replay -- --input <fixture-or-snapshot> --commands <commands.json> --out <output-dir>
npm run sim:replay -- --input tests/scenarios/p1/cases.json --case A01 --out <output-dir>
```

每个验收包包含 `manifest.json`（源码/规则/参数版本、运行端、输入种子、命令）、`summary.md`、机器可读场景结果、守恒结果、回放比较、关键输入和快照。大日志按失败种子和代表成功样例保留，摘要必须覆盖所有实际运行用例。

P1 主责 A01–A14 与 A19；A12 只验证公开窗口合同，完整随机事件行为在 P3 验收。A13/A14 使用 P0 更新后的预期。A08/A19 使用固定 NPC 意图验证资源转换，不代表真实 NPC 经济已成立。

## 失败处理与交付演示

账务差额、提前可售、隐藏信息泄露、同批卖款复用或恢复分歧为阻塞项：保存最小失败输入，修复并增加回归场景，再重跑受影响组及阶段全套。不能用“容许一分钱”或补账通过。

价格带的合同若仍无法决定受阻后的动作，返回 P0 修改规则与版本；不在代码里偷偷绕过保护。跨端差异先按 P0 数值方案定位，不能临时改成只比截图或四舍五入后的净值。

交付演示依次运行大单部分成交、同价拆单、两市场共享钱包、T+1/下一批解锁、区间外受阻和导出恢复；审阅者应能用 CLI 复现结果并核对账本。演示完成后打开阶段摘要逐条对应 P1-AC1–AC7，由实际证据签收。
